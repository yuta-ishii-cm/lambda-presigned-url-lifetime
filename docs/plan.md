# 検証計画

## 背景

数十GBのような大きなファイルを、S3マルチパートアップロードの署名付きURLでアップロードしてもらう構成を想定する。署名付きURLはLambdaが実行ロールの認証情報で発行し、有効期限（`expiresIn`）は1時間とする。

アップロード側が全パート分のURLを最初にまとめて受け取り、順番にアップロードする場合、後半のパートは発行から開始まで1時間以上待つことがある。そのため有効期限を6時間程度に延ばしたい。

ただし、一時的な認証情報で署名したURLは、`expiresIn` に関係なく認証情報の失効と同時に使えなくなる。Lambdaの実行ロールの認証情報が何時間もつかは公式ドキュメントに記載がなく、ネット上の情報も「約1時間」「最大12時間（デフォルト2時間）」などばらついている。

## 分かっていること（公式ドキュメント）

出典: [Download and upload objects with presigned URLs - Amazon S3](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)

- 一時的な認証情報で作った署名付きURLは、認証情報が失効した時点で失効する。`expiresIn` の方が長くても同じ
- 有効期限はHTTPリクエストの開始時点で確認される。期限直前に始まった転送は、途中で期限を過ぎても最後まで続く
- EC2のインスタンスプロファイルは約6時間、ECSのタスクロールは1〜6時間ごとに更新される、とは書かれている。Lambdaの記載はない
- IAMユーザーの認証情報で署名すれば最大7日有効
- Lambdaの実行ロールからさらにAssumeRoleする（ロールの連鎖）と、セッションは最大1時間に制限される

## 知りたいこと

1. Lambdaの実行ロールの認証情報で署名したURLは、実際に何時間有効か
2. 実行環境の起動からの経過時間で変わるか（起動直後に発行したURLと、長く起動しっぱなしの実行環境で発行したURLの比較）
3. 同じ実行環境の中で、認証情報が途中で更新されることはあるか
4. 1〜3の結果から、`expiresIn` を6時間にしたとき、どの条件でも6時間もつと言えるか

## 計測方法

### 考え方

- `expiresIn` を上限の7日（604800秒）にしてURLを発行する。こうすると、URLが使えなくなった時刻＝認証情報が失効した時刻になり、認証情報の寿命そのものを測れる
- URLはバケット内の小さな固定オブジェクト（例: `probe.txt`）を取得する `GetObject` 用でよい。署名と認証情報の仕組みはマルチパートアップロードの `UploadPart` と同じ
- 確認は5分おきにGETして、最初に失敗した時刻とエラーコード（`ExpiredToken` / `AccessDenied` など）を記録する。時刻の精度は5分

### 構成案

| 要素 | 役割 |
|---|---|
| S3バケット | `probe.txt` と、発行したURLの記録・計測結果を置く（作成済み） |
| 発行Lambda（常時起動用） | 5分おきに定期実行して実行環境を起動させたままにし、呼ばれるたびにURLを1本発行して記録する |
| 発行Lambda（コールドスタート用） | 1〜2時間おきにだけ呼び、毎回ほぼ新しい実行環境でURLを発行する |
| 確認Lambda | 5分おきに、まだ生きているURLを全部GETし、失敗したら失効時刻として記録する |
| 定期実行 | EventBridge Scheduler |

発行Lambdaは、URLと一緒に次の値を記録する。

- 発行時刻
- 実行環境ID（モジュールのトップレベルで1回だけ作るUUID）
- 実行環境の初期化時刻（同じくトップレベルで記録する時刻）と、発行時点での経過時間
- その実行環境での呼び出し回数と、コールドスタートだったか
- アクセスキーIDの末尾4文字（`AWS_ACCESS_KEY_ID` から。認証情報が更新されたかを見分けるため。全体は記録しない）

常時起動用でも、Lambdaは数時間で実行環境を入れ替えることがある。その入れ替わりのタイミングも、実行環境IDと初期化時刻から分かるので結果として残す。

### 期間

「最大12時間」説を確かめるため、24時間以上回す。終わったら定期実行を止めて `cdk destroy` する。

## 注意

- 署名付きURLにはセッショントークンが入っている。URLそのものはバケットの中にだけ置き、git・ブログ・ログには出さない。集計結果にも含めない
- アクセスキーIDは末尾4文字だけ記録する
- 記録先はS3に決めた（1URLにつき1つのJSON）。SDKの依存を増やさずに済み、確認Lambdaの更新も1オブジェクトの上書きで足りるため
  - 確認中は `records/live/{id}.json`、GETの失敗を確認したら `records/failed/{id}.json` に移し、以後は確認しない
  - 確認Lambdaは、成功するたびに `lastOkAt`（最後に成功した時刻）を更新する。失効時刻は「`lastOkAt` より後、失敗を検知した時刻以前」と幅で分かる
  - 4xxはURLが使えなくなったものとして記録する。5xx・タイムアウト・通信エラーは一時的な失敗として記録せず、次の確認でもう一度GETする
  - `ExpiredToken` のエラーレスポンスには `<Token-0>` としてセッショントークンが入るため、レスポンス本文は保存・ログ出力せず、`Code` と `Message` だけを取り出す
- コールドスタート用の発行Lambdaは1時間おきに呼ぶ。実際にコールドスタートだったかは記録の `isColdStart` で確かめる

## 作業の進め方（引き継ぎ）

初期セットアップ（依存関係、tsconfig、CDKのひな形、S3バケット）までは済んでいる。次の順で進める。

1. 発行Lambdaを実装する（`src/handlers/issue.ts`）。実行環境の情報を集める部分は純粋関数に分けてテストする
2. 確認Lambdaを実装する（`src/handlers/check.ts`）
3. `infra/stack.ts` にLambda2種（発行は常時起動用とコールドスタート用の2つ）とEventBridge Schedulerを追加する
4. 結果を集計するスクリプトを `scripts/` に作る（実行環境の経過時間と、URLがもった時間の関係が見られる表）
5. デプロイして24時間以上回し、結果を `docs/results.md` にまとめる
6. ブログ原稿を `articles/`（git管理外）に書く
